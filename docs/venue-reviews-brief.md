## 0. 結論

**いまは作らない。** 機能としての難易度は低いが、**投稿が集まる交通量に届いていない**。
空欄のレビュー欄が35店舗分並ぶのは、機能が無い状態より悪い。

作るとしても、一般的な「星評価＋自由記述の口コミ」ではなく
**事実レポート型**（後述 §5）にすべき。理由は §2〜§4。

再検討の発火条件は §7 に数値で置いた。

## 1. 提案の内容

店舗ページ（`/venues/<slug>/` 35ページ）に、利用者がその店のレビューを書き込める欄を設ける。

## 2. 決定的な事実 — 投稿が集まる交通量に達していない

Search Console の実測（`data/search-console/*.json`、いずれも28日窓）:

| 取得日 | 期間 | サイト全体クリック | 店舗ページ 合計クリック | 店舗ページ 合計表示 |
|---|---|---|---|---|
| 2026-09-04 | 08-05〜09-01 | 265 | **8** | 487 |
| 2026-09-07 | 08-08〜09-04 | 319 | **15** | 658 |
| 2026-09-14 | 08-15〜09-11 | 498 | **25** | 1,164 |

直近28日で、**全店舗ページを合計して25クリック**。サイト全体の約5%でしかない。
34ページに割ると **1店舗あたり月0.7クリック**。

UGCは訪問者のごく一部しか書かない（一般に投稿率は0.1〜1%オーダー）。
月0.7訪問の店舗ページに投稿が付く確率は、事実上ゼロである。
**35個の「まだレビューはありません」が並ぶ**という結果が最も確実な予測になる。

一方で**表示回数は 487 → 658 → 1,164 と約5週で2.4倍**に伸びている。
店舗ページのCTRは 25/1,164 = **2.1%**（サイト全体は13.0%）で、
いま投資すべきは「投稿欄」ではなく**タイトル・説明文の改善によるCTR回収**の側である。

> **この節がこの企画メモで最も重い。** 以下の §3〜§6 の論点は、仮に交通量が足りていたとしても
> 残る課題であって、交通量の不足はそれ以前の問題である。

## 3. 「特定店舗を評価しない」という既存方針との衝突

`fukuoka-poker-navi` の README には、明文化された立場がある。

> レビュー部申し送り＝「**特定店舗を評価しない**」立場をリンク構造でも崩さないため

これは文章上の宣言にとどまらず、**コードで機械的に担保されている**:

- `tools/gen-guide-webcoin-regulation.js` の `verify()` は、生成物に `/venues/` へのリンクが
  1件でも混入したら**異常終了する**
- `gen-guide-pages.js` とあえてファイルを分けてあり、その理由も
  「店舗リンクが誤って紛れ込むリスクがあるため」と同ファイル冒頭に書かれている

店舗ごとの星評価・口コミの掲載は、**この方針の撤回**にあたる。
機能追加の可否ではなく、**サイトの立場の変更**として判断する必要がある。

なお §5 の事実レポート型は、「評価」ではなく「事実の補完」なので、この方針と両立しうる。
ただし境界線（どこからが評価か）を先に決めておかないと、運用で崩れる。

## 4. 事業構造・法務上の論点

### 4-1. PR有料掲載枠との利益相反

このサイトの収益源は「広告・**店舗PR有料掲載枠**・アフィリ」。
低評価が付いた店がPR枠の顧客でもある構図になると、削除対応のたびに
**「金を払えば悪い口コミが消える」**という疑いが立つ。29〜35店舗の狭い界隈では、
1件の削除対応が掲載店全体との関係に波及する。

対応するなら、削除基準を先に公開し、掲載枠の有無で扱いを変えないことを明文化する必要がある。

### 4-2. 法務（打ち込み型＝自由記述を採る場合）

匿名の第三者投稿を受け付ける以上、運営に次の負担が乗る。
**リスクの大きい順**に並べた。

#### (A) 業種特有 — 換金・レートへの言及【最大】

「この店は換金できる」「レートは◯◯」といった投稿が来たとき、**掲載し続けることは
掲載店にとって致命的**であり、かつサイトが違法情報の流通に関与したと見られかねない。
2025年12月の警視庁一斉調査を受けている業界であり、当サイト自身が
`guide/webcoin-regulation/` でその解説記事を持っている領域である。

投稿が事実であっても虚偽であっても、どちらでも運営が困る構造になっている点が重い。

- **回避策**: 換金／レート／時給／闇 等のNGワードで**自動的に保留**へ落とす。
  自動公開の経路に絶対に乗せない。保留分は人が判断する。

#### (B) 発信者情報開示請求に応じられない【設計上の致命点】

改正プロ責法（2022年10月〜）の発信者情報開示命令（非訟手続）が来たとき、
**ログを持っていなければ開示できない**。開示できないと、被害を主張する店舗の
矛先が投稿者ではなく**運営者本人**に向かう。

- **★Google Forms は投稿者のIPアドレスを記録しない。**
  §5 の「`contact.html` と同じ方式」は、事実レポート型では成立するが
  **打ち込み型では成立しない**。ここは設計を分けること。
- **回避策**: 独自ドメイン配下のサブドメイン（例 `api.fukuokapoker.com`）を
  Cloudflare Workers 等に向け、`CF-Connecting-IP` とタイムスタンプを保存する。
  保存期間（3〜6ヶ月程度）を決め、プライバシーポリシーに明記する。
  bot対策（Turnstile 等）も同じ層で入る。

#### (C) 名誉毀損・信用毀損・業務妨害と、削除義務

相手は法人・個人事業主なので、**実際に請求が来る前提**で設計する。
スタッフ個人に言及した投稿は、店舗ではなく個人の名誉・プライバシーの問題になる。

**★承認制のパラドックス**:
情プラ法（情報流通プラットフォーム対処法、2025年4月施行。旧プロバイダ責任制限法）の
免責は、「権利侵害を知らず、知り得る相当の理由も無かった」場合に働く。
**事前承認制は全投稿を読むので、この免責を自ら外すことになる。**
被害の発生自体は防げるが、通した1件の責任は重くなる、というトレードオフがある。

- 逆に言えば、**§5 の事実レポート型は評価語を持たないので承認判断が容易**で、
  承認制と相性が良い。打ち込み型＋承認制は、運営が毎回
  「この文章は違法か」を法的に判断し続ける運用になる。
- なお情プラ法が課す**大規模事業者向けの義務**（申出窓口の公表・調査と通知の期限など）は
  規模要件があり、当サイトは非該当の見込み。ただし削除申出への対応と
  開示請求への対応は、規模に関係なく生じる。
- **回避策**: 削除基準を策定して公開し、窓口を設置する。掲載枠の顧客か否かで
  扱いを変えないことを明文化する（§4-1）。掲載店側の反論を載せる経路も用意する。

#### (D) 景表法のステマ規制（2023年10月〜）

自社・関係者による投稿、投稿への対価付与は即アウト。
措置命令の対象は「表示をした事業者」なので、運営者が自ら投稿すれば自社の表示になる。

- **回避策**: 対価の禁止と掲載店関係者の投稿禁止を規約に明記。
  PR有料掲載枠とレビュー欄を視覚的・構造的に分離し、PR枠である旨を明示する。

#### (E) 利用規約が存在しない／プライバシーポリシーが投稿を想定していない

**現状の確認結果**:
- `about.html` `privacy.html` `contact.html` はあるが、**利用規約ページが無い**。
  投稿文の著作権は投稿者にあるため、掲載・改変・転載の**利用許諾を得る根拠が無い**。
- `privacy.html` は9章構成（取得する情報／利用目的／第三者提供／アクセス解析／広告／
  Cookie／掲載情報の正確性／変更／問い合わせ窓口）で、
  **投稿およびログ保持に関する記述はゼロ**。

- **回避策**: 利用規約の新設と、プライバシーポリシーの改訂（(B)のログ保持を含む）を
  **機能公開より先に**行う。個人情報取扱事業者としての利用目的の特定・公表・安全管理措置も
  この改訂で満たす。

### 4-3. 運用コスト

上記の帰結として、**モデレーション体制が機能より先に要る**。
承認制にすれば投稿は止められるが、承認する人の時間が継続的に必要になる。
「作って放置」ができない種類の機能である点が、このサイトの他の自動化とは性質が違う。

### 4-4. SEO

> **★初版の訂正**: 本節に初版で
> 「`AggregateRating` の構造化データは自己申告扱いで、リッチリザルトはほぼ出ない」
> と書いたが、**この案件では不正確だった**。Googleのレビュースニペットの自己申告制限は
> 「**自社（および関係者）が自社について書いたレビュー**」に掛かるもので、
> 第三者である本サイトが**他社である掲載店について**集めたレビューは対象外である。
> つまり星マーク表示の対象になり得る（食べログ型）。
> **SEO上のプラス幅は初版の記述より大きい。**

#### プラス側

- **「店名 口コミ」「店名 評判」クエリの獲得。** 現在拾えているのは「店名＋日程」中心
- **店舗ページの独自性の向上。** 現在 表示1,164 に対しCTRは2.1%（サイト全体13.0%）で、
  `title` / `description` が全店ほぼ同一テンプレートであることが一因。
  レビュー本文があれば店ごとの差分を作れる
- 一次体験にもとづく情報は、Googleが評価すると明言している領域にあたる
- レビュー数が一定以上積まれれば、レビュースニペット（星）表示の可能性

#### マイナス側（いずれも**投稿件数に従属**する）

- **0件の店の定型文。** 「まだレビューはありません」が35ページに並ぶと定型文の水増しになる
  → **回避可能**: `tools/gen-venue-pages.js` で**0件の店はセクションごと出力しない**分岐を入れる。実装は軽い
- **ユーザー生成スパム。** Search Console の手動対策には「ユーザー生成スパム」という
  独立した項目がある。放置された投稿欄は狙われる
- 実体の薄いレビューに構造化データを付けると、スパム的な構造化マークアップの手動対策リスク
- Googleマップの口コミと内容が重複するだけなら、独自価値が無い

#### 「評価しない」方針の撤回による内部リンクの上積みは、ほぼ無い

方針変更の副次効果として「ガイド記事から店舗ページへの内部リンク解禁」を期待したが、
**実際に数えた結果、期待できない**。

| ページ | `/venues/` への内部リンク数 |
|---|---|
| `guide/beginner/` | 89 |
| `guide/webcoin-regulation/` | **0**（方針の歯止めが効いているのはここだけ） |
| `areas/nakasu/` | 419 |
| `areas/kitakyushu/` | 363 |
| `areas/tenjin/` | 329 |
| `areas/kurume/` | 206 |
| `areas/ohashi/` | 140 |
| `areas/imaizumi/` | 59 |
| `areas/daimyo/` | 3 |

店舗ページは内部リンクで孤立していない。CTR 2.1% の原因は
`title` / `description` の同質性やクエリ意図側にあると見るべきで、
内部リンク構造ではない。

#### SEOとしての結論

**上振れは実在するが、投稿件数に完全に従属する。**
§2 の交通量（店舗ページ合計で28日25クリック）では件数が積まれないため、
**SEOは先行実装の根拠にならない**。§7 の発火条件を満たしてからの話になる。

## 5. 作るとしたらの設計（案A・推奨） — 事実レポート型

星評価と自由記述をやめ、**「行った人が事実だけ報告する」**形にする。

### 収集項目（案）

| 項目 | 形式 | 意図 |
|---|---|---|
| 初期スタック／レベル時間 | 数値 | 掲載中のストラクチャー情報の裏取り |
| 実際の開始遅延 | 選択（定刻/15分以内/30分以上） | 利用者が最も困る実害 |
| 待ち時間・満席の有無 | 選択 | 行動判断に直結 |
| 初参加者の割合（体感） | 選択 | 初心者バッジの裏付け |
| 喫煙可否・分煙 | 選択 | 現地でしか分からない |
| 駐車場・近隣コインP | 選択＋自由記述（短） | 同上 |
| 支払い手段 | 選択 | 同上 |

**「楽しかった」「店員の態度が悪い」といった評価語は項目として持たない。**
これが §3 の方針と両立させるための線引きになる。

### フロー

```
利用者が投稿（Google Forms へ直POST）
   → 人が承認（スプレッドシート上で可否判断）
   → data/venue-reports.json へ反映
   → tools/gen-venue-pages.js で再生成 → コミット → 公開
```

`contact.html` に既に**同じ方式の前例がある**（`FORM_ACTION` に `no-cors` で
`docs.google.com/forms/.../formResponse` へPOST）。バックエンドは不要で、
サーバ費用も新規の秘密情報も増えない。

### 前提（ホスティングの事実確認・2026-09-15）

**独自ドメイン `fukuokapoker.com` で公開されている**（`CNAME` ファイル）。
ただし**その土台はGitHub Pages**である。リポジトリ自身のコメントが明言している:

> このリポジトリは build_type: legacy (source: main ブランチ / ルート) で
> **GitHub Pages に配信されている** — `_config.yml` 冒頭

`CNAME` ファイルの存在自体が GitHub Pages のカスタムドメイン機構であり、
`.github/workflows/` にもデプロイ系のワークフローは無い（5本すべてデータ取得・監視系）。

→ **「独自ドメインがある」ことと「バックエンドがある」ことは別。**
  サーバ側で動くものは現状ひとつも無い。

→ ただし**ドメインとDNSを握っていることは有利**に働く。
  `api.fukuokapoker.com` のようなサブドメインを Cloudflare Workers 等に向ければ、
  同一ドメイン配下に投稿APIを置ける。**§4-2 (B) のログ保持要件は、この構成でしか満たせない。**

### 技術的な制約（守るべきこと）

- `venues/*/index.html` は `tools/gen-venue-pages.js` の**完全生成物**で、
  `--check` が**バイト一致を検証**している。
  → **生成物の決定性は絶対に崩さない**。投稿内容はあくまで
  「入力データ（`data/venue-reports.json`）→ 再生成」の経路で入れる。
  クライアント側で外部JSONを取ってきて描画する方式は、決定性は保てるが
  **未承認の内容がそのまま公開される経路**を作るので採らない。
- JSON-LD に `Review` / `AggregateRating` は**足さない**（§4-4）。
- 掲載の有無・順序が店舗間で恣意的にならないよう、
  `tools/venue-listing-rules.js` と同じ考え方で規則をコード側に置く。

## 5-2. 案B — 一般的な口コミ型（星評価＋自由記述）

採るなら、**機能実装の前に**次が揃っている必要がある（詳細は §4-2 / §4-4）。

1. 「特定店舗を評価しない」方針の撤回（社長判断・README の該当記述の更新）
2. **利用規約の新設**（現在ページが存在しない）と、投稿文の利用許諾条項
3. **プライバシーポリシーの改訂** — 投稿・IPログの保持と保存期間（現在は記載ゼロ）
4. **投稿受付をGoogle Formsにしない** — IPが取れず開示請求に応じられない（§4-2 (B)）。
   サブドメイン＋Cloudflare Workers 構成にする
5. **NGワードによる自動保留**（換金／レート／時給 等）— §4-2 (A)
6. 削除基準の策定と公開、削除申出の窓口設置、掲載店の反論経路
7. モデレーション担当と、対応SLAの取り決め（承認制のパラドックスを理解した上で選ぶ）
8. PR掲載枠の顧客と非顧客で扱いを変えないことの明文化
9. 対価の禁止・掲載店関係者の投稿禁止（ステマ規制）
10. `gen-venue-pages.js` に「0件の店はセクションごと出力しない」分岐（§4-4）

**機能の実装量より、この10点の整備の方が圧倒的に重い。**
うち 1〜3・6〜9 はコードではなく**文書と体制**の仕事である。

## 7. 再検討の発火条件（数値）

次のいずれかを満たしたら、この企画メモを開き直す。

- **店舗ページ合計のクリックが、28日窓で 300 以上**（＝1店舗あたり月10弱）
  — 現在25。§2 の伸び（8→15→25）が続けば、単純外挿で半年前後
- 店舗ページのCTRが 5% 以上に回復（現在2.1%）
- 掲載店側から「利用者の声を載せたい」という要望が複数件入る
  （受け身の導線でこれが来るなら、投稿も集まる可能性が高い）

測定はすべて既存の `data/search-console/*.json`（`fetch-search-console` ワークフロー）で足りる。
**新しい計測の追加は不要。**

## 8. いま代わりにやる価値があること

§2 のとおり、店舗ページは**表示は伸びているのにクリックされていない**（CTR 2.1% / サイト全体13.0%）。
投稿欄より先に、この1,164表示の取りこぼしを回収する方が期待値が高い。

- 店舗ページの `title` / `meta description` の見直し（現在は全店ほぼ同一テンプレート）
- 検索クエリ側の実データ（`data/search-console/*.json` の `queries`）と
  店舗ページのタイトルの突き合わせ

これは本企画メモの範囲外なので、別途起票する。
